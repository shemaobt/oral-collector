# Noridoc: sync

Path: @/lib/features/sync

### Overview

- Owns the app's connectivity signal, the upload queue for local recordings, and the offline-aware policy that every other feature is expected to honor.
- Exposes `syncNotifierProvider` (synchronous `SyncState.isOnline`) as the canonical "are we online?" check used across notifiers, screens, and providers.
- Hosts the `SyncEngine` that drains the local recordings queue (Drift-backed) to the server, and `BackgroundSyncService`, a periodic timer (web and iOS) that re-triggers the queue. On Android the queue is instead kept alive while the app is minimized by the upload foreground service (see `@/lib/features/sync/data/services/docs.md`).

### How it fits into the larger codebase

- Other features import `syncNotifierProvider` from `@/lib/features/sync/presentation/notifiers/sync_notifier.dart` and gate any API call on `state.isOnline`. See `@/lib/features/home/presentation/home_screen.dart` for the canonical reconnect-listener shape.
- The `SyncEngine` depends on `@/lib/features/recording/data/repositories/local_recording_repository.dart` (Drift table of pending uploads) and `@/lib/core/network/authenticated_client.dart`. Recordings are created locally first; the engine reconciles them with the server on its own schedule.
- The engine drains the queue **in the order `getPendingUploads` returns it** (FIFO). That order is `createdAt ASC, id ASC` and is owned by `LocalRecordingRepository` (ENG-122): `createdAt` is true enqueue time, `id` is the same-second tiebreaker. The engine itself adds no `ORDER BY`; if the repository's ordering changed, the queue's drain order would change with it. See `@/lib/features/recording/data/repositories/docs.md` for why `recordedAt` is unsafe here.
- The upload pipeline runs in-process through Riverpod: `syncEngineProvider` builds `SyncEngineImpl` with the shared `authenticatedClientProvider` (`@/lib/core/network/authenticated_client.dart`), which reads the access token from `flutter_secure_storage` via `@/lib/core/providers/secure_storage_provider.dart` (the store `@/lib/core/auth/auth_notifier.dart` writes to). Keeping the Android process alive via the foreground service is what lets that in-process credential read keep working while the app is backgrounded; there is no out-of-process worker.
- Connectivity flips originate in `connectivity_plus` and flow through `ConnectivityServiceImpl` → `SyncNotifier._onConnectivityChanged`, which triggers `processQueue()` on offline → online. Screens that need to refresh their own data on reconnect register their own `ref.listen` (the sync layer doesn't notify them directly).
- The global HTTP client at `@/lib/core/providers/http_client_provider.dart` enforces a 15 s connect timeout on native platforms. This is the safety net for the "Wi-Fi connected, no real internet" case that `connectivity_plus` can't detect.

### Core Implementation

- `SyncNotifier.build()` runs `_initConnectivity()` (subscribe → snapshot → refresh pending count) and the notifier never disposes itself implicitly — it's a root-level `NotifierProvider` held for app lifetime. **`_initConnectivity` subscribes to `onConnectivityChanged` BEFORE awaiting the initial `isOnline` snapshot (ENG-139 F19).** `connectivity_plus`'s stream is a broadcast with no replay, so a flip that lands during the `await` would otherwise be lost. A `_sawConnectivityEvent` flag records whether a live event arrived during that window; if it did, the now-stale snapshot is dropped rather than allowed to clobber the fresher value the event already wrote. `_onConnectivityChanged` sets the flag on every event.
- `SyncState` is intentionally synchronous: `isOnline` is a plain bool so callers can do `ref.read(syncNotifierProvider).isOnline` in `initState` / `fetch*` methods without awaiting. The async `connectivityServiceProvider.isOnline` exists for the one early-boot caller in `@/lib/core/auth/auth_notifier.dart` — `refreshSessionIfOnline` (the network half of `tryAutoLogin`, ENG-139 F8) — which runs before Riverpod state has been seeded.
- `SyncEngine.processQueue` filters the pending Drift rows on three conditions — `retryCount < kMaxUploadRetries` (the shared constant in `@/lib/core/config/upload_retry_policy.dart`, which `LocalRecordingRepository.markAsFailed` reads from too), the row is **not** already in `uploading`, and the row is outside its backoff window — then uploads either serially or with `maxConcurrency: 3` on Wi-Fi. Each upload runs the create → upload-url → PUT → confirm pipeline via `ResumableUploadService`. **Connectivity is sampled once per pass, not once per item (ENG-125):** the pass-level gate probes `isOnline` (and `isOnWifi` when `wifiOnly`) before the drain begins; the per-item loops re-probe **only when an upload actually fails**, so a mid-pass network drop still aborts the queue promptly (the serial loop `break`s; the concurrent loop sets a `stopAdmitting` flag so in-flight uploads drain but no new ones start) without polling on the happy path. `_uploadRecording` returns an internal `_UploadOutcome` (uploaded / skipped / failed) so the loops can branch on failure. The storyteller drain (`_processPendingStorytellers`) still probes per storyteller — out of scope for that change. The backoff window is computed by the top-level pure function `backoffWithJitter(attempt, random)`: it returns the ladder rung for the attempt (`5s, 15s, 30s, 60s`, saturating at the last rung) plus additive random jitter in `[0, base*0.5]`, so the effective delay lands in `[base, 1.5*base]`. The jitter de-synchronizes devices that failed at the same instant (e.g. when a server outage clears) so their retries don't realign on one schedule (thundering herd); it never shortens a delay below the base rung. Both the recordings drain and the storyteller drain share one private helper (`_isWithinBackoffWindow`) over a single `Random` field, replacing the two previously-duplicated window checks.
- At app startup, before the queue or any upload listener goes live, `LocalRecordingRepository.resetStuckUploading` reclaims rows orphaned in `uploading` by a mid-upload crash (see `@/lib/features/recording/data/repositories/docs.md`). The skip of `uploading` rows in the drain and this startup reclaim are complementary: the reclaim flips orphans back to `local` so they become eligible again, while the skip keeps the drain from racing a row that is genuinely in flight (or was just reclaimed). See Things to Know.
- The recording upload path classifies failures by the typed error model (ENG-103, see `@/lib/core/errors/docs.md`), not by exception subtype. A non-2xx on the create/confirm calls is converted to an `AppException` via `throwForResponse` (`@/lib/core/network/error_boundary.dart`); the catch then routes on `AppException.retryable`. The one exception is intercepted inline at the create call, before the decode: a **409** is parked as `failed_conflict`. The other permanent-fail status, `failed_description`, is decided before the request is issued rather than from a status code (see Status vocabulary below) — retryable leaves go back to the queue via `markAsFailed` — which spends one retry and, when that was the last one, writes `failed_exhausted` itself — non-retryable leaves are stamped permanently-failed via `_markPermanentlyFailed` (whose default status is `failed_exhausted`, not the generic `failed` — see Status vocabulary below). The created recording id and the confirm `gcs_url` are read through the safe-readers (`@/lib/core/serialization/docs.md`), so a malformed field is a terminal `ParseException` rather than an uncaught `TypeError`. The storyteller sync path is deliberately untouched — it has no permanent-fail state.
- `_onConnectivityChanged` calls `processQueue()` automatically on offline → online. This handles upload resumption; it does **not** refresh feature read-paths (those are the screen's responsibility via `ref.listen`).
- Uploads use a per-call `.timeout(_apiTimeout)` (30 s) on create/confirm requests, plus a size-scaled timeout on the PUT to GCS. The 15 s connect timeout on the global HTTP client is independent of these and fires earlier when the TCP handshake never completes.

### Status vocabulary: client vs server

Several Drift columns hold a free-text status string (no DB-level enum). The values diverge between what the client writes locally and what the server returns over the wire — same column name, different vocabularies and casing. `@/docs/recording-split-semantics.md` is the authoritative field-by-field split mapping; this section just names the state machines.

| Column (client / server) | Where | Values |
|---|---|---|
| `uploadStatus` / `upload_status` | recordings | **client:** `local`, `uploading`, `uploaded`, `verified`, `failed`, `failed_conflict`, `failed_description`, `failed_exhausted`, `failed_missing_file`, `web_uploading` (web). **server:** uppercase, e.g. `VERIFIED`. `local`, every `failed_*` variant and `web_uploading` are client-only and never sent by the server. `failed` means *a retry is still coming*; the `failed_*` variants are terminal. |
| `cleaningStatus` / `cleaning_status` | recordings | **client:** `none`, `needs_cleaning`; reads `cleaned` from the server. **server:** uppercase enum, e.g. `CleaningStatus.NONE`. |
| `syncStatus` | storytellers (client-only queue) | `synced`, `uploading`, `failed`. The server tracks storytellers by id/timestamps, not this column. |
| `status` | recording_sessions (client-only recovery) | `active`, `completed`. |
| `splitting_status` | **server-only** | e.g. `NONE`, `ARCHIVED_AFTER_SPLIT`. The client schema has no equivalent column. |

- **A client `uploaded`/`verified` means "left the device and the server accepted the request" — NOT "durably stored and visible to other clients."** Server-confirmed durability is tracked by the server's own status; the client only ever reads what the server DTO mapper pulls from `upload_status` / `cleaning_status` (`serverRecordingToLocal` in `@/lib/features/recording/data/server_to_local_recording.dart`). Don't treat a local terminal status as proof of server-side completion.
- **Casing crosses the boundary.** The client writes lowercase (`verified`); the server emits uppercase (`VERIFIED`). Any comparison that spans the two must normalize, or go through the safe-readers that map the server DTO into the client's lowercase set (`@/lib/core/serialization/docs.md`).
- The drain-eligibility filter in `processQueue` keys off the client `uploadStatus`: `uploading` is skipped; `local` / `failed` are eligible subject to backoff.
- **`failed_conflict` is a terminal status with a user-driven exit (ENG-71).** The backend deduplicates `POST /api/oc/recordings` by `(project_id, title)`. `_uploadRecording` checks the create response for a 409 **inline, at that one call site**, and parks the row via the same permanent-failure path as `failed` but under `failed_conflict`, so the UI can tell a name clash from a generic upload failure. Deliberately not a `on ConflictException` catch arm around the whole upload body: only the create call deduplicates on `(project_id, title)`, so only a 409 raised *there* is a name clash, and only there does a rename clear it. A 409 raised anywhere else in the upload has no such exit — that row already has a `serverId`, so a rename skips the create branch entirely — and parking it as `failed_conflict` would advertise a way out that leads nowhere. (An earlier revision of this note offered `confirm-upload` as the example of such a 409. That was wrong: `confirm_upload` in `app/services/oral_collector/recording_service.py` loads the recording, emits the Inngest event and returns, with no conflict path at all. The reasoning above stands on its own; the example did not.) Every 409 raised outside the create call therefore falls through to the generic non-retryable handling (`throwForResponse` → `ConflictException` → `_markPermanentlyFailed`, status `failed_exhausted`). `getPendingUploads` does not match `failed_conflict`, so retrying alone can never clear it — only a rename can. Renaming through `RecordingDetailNotifier.saveDetails` calls `resetAndRetry`, which puts the row back to `local` with a fresh retry budget — but only if the server accepts the new title: `PATCH /api/oc/recordings/{id}` also 409s on a clash, `RecordingApiRepositoryImpl.updateRecording` raises `ConflictException` for it, and `saveDetails` returns `titleConflict` without writing anything, so a second clash leaves the row conflicted and re-offers the rename instead of desynchronizing the device from the server. **Visibility is split, on purpose:** the recordings list's *pending* filter (`RecordingsListState.pendingRecordings`) does match `failed_conflict`, so a conflicted recording stays visible and actionable where the user can rename it; the queue-based surfaces do not, because they read `getPendingUploads` — the header badge (`SyncState.pendingCount`, written by `SyncNotifier._refreshPendingCount`), the home counter, and the upload-queue sheet's own list all exclude it, which is correct: it is not queued work and no amount of draining will move it. `deleteStaleRecordings` (the "Clear failed" action) matches `failed` / `uploading` exactly, so it will not destroy a conflicted recording.
- **`failed_description` is the same shape, for the create rule's other refusal (ENG-354).** `POST /api/oc/recordings` requires a description of at least `minDescriptionGraphemes` (`@/lib/shared/utils/recording_description.dart`); recordings saved before that rule, and split children that inherited a short parent description, would send a null-or-short value and be refused permanently. `_uploadRecording` therefore **pre-flights** the client's own `isDescriptionSufficient` at the top of the create branch and parks the row in `failed_description` **without issuing the request** — the client owns the same rule, so it can decide up front and spend no round-trip. Scoped to the create branch on purpose: a row that already has a `serverId` sends no create, so blocking it would stop an upload the server would accept. Deliberately **not** inferred from the 422: other things 422 on that endpoint (a foreign key the caller got wrong), so reading "422" as "description" would show the wrong explanation. The pre-flight is the only place the status is decided; a 422 always falls through to the generic non-retryable handling. Same visibility split as `failed_conflict`: excluded from `getPendingUploads` (so retrying alone can never clear it, and the queue surfaces do not count it), matched by the list's *pending* filter (so it stays visible and actionable), untouched by `deleteStaleRecordings`. Exit is user-driven: the detail screen shows a banner (`recording_descriptionGapMessage`) routing into the edit-details sheet, which validates with the same predicate, and `RecordingDetailNotifier.saveDetails` calls `resetAndRetry` after a description write on such a row, putting it back to `local` with a fresh retry budget. Unlike a rename there is no server-side second refusal to guard against — the description is only sent at create time — so the write is unconditional. The card and `RecordingStatusSection` give it its own label (`recording_statusDescriptionTooShort`) so it never reads as a generic "Failed". The plain `onRetryUpload` affordance excludes it, like `failed_conflict`: a bare retry would hit the same pre-flight.
- **`failed_exhausted` and `failed_missing_file` close the two ways a row used to be queued and unreachable at once (ENG-377).** `getPendingUploads` matched `local` / `failed` / `uploading` without reading `retryCount`; `processQueue`'s eligibility filter dropped anything at `retryCount >= kMaxUploadRetries`. A row at (`failed`, budget spent) satisfied the first and was refused by the second, forever: the badge counted it, the chip stayed lit, and tapping sync drained zero items and returned without an error to show — `SyncState` has no error field, so nothing could explain it. This was not an edge case: `_markPermanentlyFailed` wrote `failed` **and** `retryCount: maxRetries` in one write, so every non-retryable failure produced it, and the retryable path produced it too on the attempt that spent the last retry. `_markPermanentlyFailed` now defaults to **`failed_exhausted`**, and the budget path is decided inside `LocalRecordingRepository.markAsFailed` rather than by the engine. That placement is the fix, not a detail: the engine could only make that call from a row it had already read, so a failure raised before the read — the platform-channel call inside `_resolveFilePath`, the relocated-path `updateRecording`, the `getRecordingById` itself — counted from zero and left the row at `failed` with a spent budget anyway. `markAsFailed` is the method that re-reads the count, so deciding there makes the invariant hold whatever threw and wherever. The opposite dead end was the file-not-found branch: `_resolveFilePath` returning null called `markAsFailed(incrementRetry: false)`, so the count never advanced, the row never reached the ceiling, and every pass reselected it and skipped it again. That branch now writes **`failed_missing_file`**, terminal because `_resolveFilePath` has already tried all three locations the app uses and deletion is a hard delete — the file is not coming back. Same visibility split as the two statuses above: out of `getPendingUploads` (so the counters, the queue sheet and the drain all stop seeing them), matched by the list's *pending* filter, and untouched by `deleteStaleRecordings` — not because the audio survives (`failed_missing_file`'s does not, by definition) but because each row still carries the title, description and classification the user typed and the server never received. Exits differ: `failed_exhausted` gets a retry banner routed through `resetAndRetry`, and is the one terminal status `onRetryUpload` does include, because a retry is exactly what it needs; `failed_missing_file` is offered a delete instead, since retrying cannot conjure the audio back. **Rows already stuck on a device are healed by a startup sweep, not just the writer fix.** `LocalRecordingRepository.normalizeExhaustedUploads()` runs once per launch from `@/lib/main.dart` — right after `resetStuckUploading`, before the sync queue or any upload listener goes live — and retires every row still sitting at (`failed`, `retryCount >= kMaxUploadRetries`) to `failed_exhausted` in one `UPDATE`. It is idempotent by construction: the `failed` clause stops matching a row the instant it is retired, so every launch after the first is a no-op for that row. This is the piece that makes the fix visible to whoever reported the bug — fixing the three writers alone would only stop new rows from getting stuck in this shape; it would do nothing for the rows already on their device. The sweep runs from a background `Future.microtask` after the splash gate (`appStartupProvider`) resolves, not before the app's first frame, so there is a real window on every cold start where the list/detail screens can still render a `failed` row with a spent budget before the sweep flips it. `RecordingStatusSection` keeps a literal `retryCount >= 5` branch at `failed` for exactly that window — a literal and not `kMaxUploadRetries`, because it describes what older builds wrote, not the ceiling in force; it renders the same `detail_maxRetries` line `failed_exhausted` uses, so the two paths agree regardless of which one a given frame catches the row in.

### Things to Know

- **Online check is interface-level, not reachability-level.** `connectivity_plus` reports only the OS interface state (Wi-Fi / cellular / none). A captive portal or dead AP still reports online. The 15 s connect timeout in `@/lib/core/providers/http_client_provider.dart` is the current mitigation — it fails fast instead of waiting the OS default (~30 s). A real reachability probe (e.g. `internet_connection_checker_plus`) is a deliberate follow-up, not implemented here. `ConnectivityServiceImpl.isOnline` is uncached, so each call is a real OS query; `processQueue` samples it **once per pass** at the gate and re-probes only after a failed upload (ENG-125) rather than before every item, so the happy path is one probe per pass.
- **The 15 s connect timeout applies only to TCP handshake, not in-flight bytes.** Long uploads/downloads are unaffected once the connection is established. Web uses the bare `http.Client()` because `dart:io HttpClient` is not available there.
- **`syncOne` and `processQueue` are mutually exclusive — bail-if-busy, not serialize.** A single `_isProcessing` flag guards both of the "leaf" upload operations in `@/lib/features/sync/presentation/notifiers/sync_notifier.dart`: whichever starts first wins, and a second upload op that finds the flag set returns immediately rather than queueing behind the first. This keeps two runs from interleaving shared upload state (`uploadingId`, per-file progress, speed samples) or stopping the Android foreground service in one run's `finally` while the other is still uploading. Methods that *delegate* to a leaf — `resetAndRetry` (→ `syncOne`), and `syncAll` / `retryFailed` / the reconnect handler (→ `processQueue`) — must NOT take the guard themselves; a re-entrant acquire would make the inner leaf bail and silently skip the upload, so only the leaf operations acquire it. Accepted gap: tapping reset-and-retry while the queue is running resets the retry count but skips the immediate upload, so that item is picked up by the next `processQueue` run.
- **`getPendingUploads` surfaces `uploading` rows, but the engine drain filters them out.** This split is deliberate: the repository query still returns `uploading` rows because the UI (`@/lib/shared/widgets/upload_queue_sheet.dart`) and the counters (`@/lib/features/home/presentation/notifiers/home_notifier.dart`) rely on seeing in-flight work. `getPendingUploads` itself was deliberately NOT narrowed. The eligibility filter inside `processQueue` is the only place `uploading` is excluded, which keeps an in-flight upload from being dispatched a second time and narrows a latent double-dispatch window between `uploadSingle` and `processQueue` — a timing-dependent mitigation, not a hard close: `uploadSingle` does not take the engine's `_isProcessing` guard, so it only helps when the `processQueue` snapshot is read after `uploadSingle` has flipped the row to `uploading`.
- **Stuck-`uploading` recovery is the deterministic crash-recovery path, and it is non-destructive.** A mid-upload app crash leaves a row stuck in `uploading`. `LocalRecordingRepository.resetStuckUploading` runs once at startup (in `@/lib/main.dart`) and flips every such row back to `local`, writing ONLY the `uploadStatus` column — `retryCount`, `lastRetryAt`, `resumableSessionUri`, `serverId`, and `uploadedBytes` are preserved, so the upload RESUMES from its saved offset rather than restarting and the retry budget stays intact. It targets `local` (not `failed`) on purpose: `deleteStaleRecordings` (the user-triggered cleanup) deletes `failed`+`uploading` rows, so landing on `local` keeps a recoverable recording clear of that destructive path. It runs unconditionally, after the startup gate resolves (`appStartupProvider` / `restoreSession`, see `@/lib/core/startup/docs.md`) and before the background-sync init / upload listeners, so the queue never observes stale `uploading` state. `uploading` is native-only (web uses `web_uploading`), so on web the call is a harmless no-op.
- **Existing offline-aware notifier flavors** — keep these in mind when adding new ones:
  - SharedPreferences hydrate-then-fetch: synchronous JSON load in `Notifier.build`, then `_fetchRemoteData` guarded by `isOnline`. See `@/lib/features/project/presentation/notifiers/project_notifier.dart`.
  - Drift cache-first, network-overwrite: load local rows first, then conditionally call API. See `@/lib/features/storyteller/presentation/notifiers/project_storytellers_notifier.dart` and `@/lib/features/recording/presentation/notifiers/recordings_list_notifier.dart`.
  - Secure-storage hydrate + async `connectivityServiceProvider`: only used at app boot by `refreshSessionIfOnline` (the network half of `tryAutoLogin`, see `@/lib/core/auth/docs.md`).
- **A failed upload is retried or terminal by the error's `retryable` flag, and the threshold case is HTTP 429.** The catch in the recording-upload path no longer keeps its own retryable/non-retryable exception taxonomy; it reads `AppException.retryable`. The load-bearing consequence is that a `429` during create/confirm is now retried (it maps to a retryable `ValidationException`) where it previously stranded the row as permanently-failed. `markAsFailed` keeps the row in the backoff queue until the attempt that spends the last retry, which it writes as `failed_exhausted` itself; `_markPermanentlyFailed` is the engine's own terminal write, for refusals that were never about the budget. A non-JSON response body (`FormatException`) and a malformed id/`gcs_url` (`ParseException`) are both terminal — retrying cannot fix a contract violation. `Error` subtypes (e.g. `TypeError`) are intentionally not caught and propagate as bugs.
- **Writes do not queue offline (except recording uploads).** Storyteller create/update/delete, invite accept, and similar mutations hard-fail offline with a snackbar. The `SyncEngine` queue is purpose-built for recording file uploads only; a generic outbox is a future feature.
- **Independent awaits in `SyncNotifier` run concurrently, not serialized.** The local-storage reporting and cache-clear helpers (`getLocalStorageUsed`, `clearLocalCache`, `getStorageSnapshot`) fan their per-file / independent reads out with `Future.wait` rather than awaiting in a loop; ordering-dependent steps stay sequential (e.g. `clearLocalCache` still deletes each file before dropping the row that points at it).
- **`clearLocalCache` only drops what the server is holding.** It reads
  `uploadStatus` **and** `serverId`, and deletes the file and row only when both
  say the upload finished — `markAsUploaded` writes them together, so a row
  claiming `uploaded` with no id never completed the round trip and is kept. It
  returns how many recordings it refused to delete, and the profile screen names
  that number instead of reporting a flat success. It used to delete every file
  and call `deleteAllRecordings()`, which cost a field user an hour-long
  recording that had waited days to upload; the dialog in front of it said
  "uploaded recordings on the server will not be affected", which is true, and
  is what made it dangerous — it answered for the recordings that were safe and
  said nothing about the ones that existed nowhere else. Freeing space is still
  the point; the recordings that are not on the server are not cache. These are fast local operations, so the fan-out is unbounded — the bounded `mapBounded` primitive is reserved for network/server batches (see `@/lib/core/util/docs.md` and ADR-0004). The upload-running fan-out is unrelated and stays under the `_isProcessing` guard above.
- **Cold-start race (tracked in ENG-62).** `SyncState.isOnline` defaults to `false` and is only updated after `_initConnectivity()` resolves (a few ms after `build()`). Until ENG-62 lands, the canonical reconnect listener on long-lived screens is what triggers the first real network fetch when a user cold-starts the app while online — don't skip the listener. Symptom if you skip it: cold-start online shows the cache (or empty) and never advances until the user manually triggers a refresh.
- **`clearStaleRecordings` returns `null` when offline mid-op.** The screen pre-checks `isOnline` before showing the confirm dialog, so the `null` path is purely a defense for the race where connectivity drops between confirm and the API call. The local cleanup is also skipped — that prevents the local row set from drifting out of sync with the server's view until reachability is restored. (A return of `0` always means a real "0 deleted" success.)
- **Checklist for any new screen / notifier that reads from the network:**
  1. Never call the API in `initState` without checking `syncNotifierProvider.isOnline` first.
  2. The notifier `fetch*` method MUST self-guard with `isOnline` as defense-in-depth, even if every caller already does.
  3. First paint renders from cache (Drift / SharedPreferences) or a meaningful empty/loading state — never block on the network.
  4. Long-lived screens add a reconnect listener: `ref.listen(syncNotifierProvider.select((s) => s.isOnline), ...)` and re-call `fetch*` on offline → online. Mirror the shape in `@/lib/features/home/presentation/home_screen.dart`.
  5. Network-required writes hard-fail offline with a snackbar; they do not queue.
