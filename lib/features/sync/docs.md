# Noridoc: sync

Path: @/lib/features/sync

### Overview

- Owns the app's connectivity signal, the upload queue for local recordings, and the offline-aware policy that every other feature is expected to honor.
- Exposes `syncNotifierProvider` (synchronous `SyncState.isOnline`) as the canonical "are we online?" check used across notifiers, screens, and providers.
- Hosts the `SyncEngine`, which drains three Drift-backed queues to the server on one pass, in order — (ENG-403) the metadata outbox for offline edits to a recording the server already has, storyteller writes, then recording uploads — plus `BackgroundSyncService`, a periodic timer (web and iOS) that re-triggers the queue. On Android the queue is instead kept alive while the app is minimized by the upload foreground service (see `@/lib/features/sync/data/services/docs.md`).

### How it fits into the larger codebase

- Other features import `syncNotifierProvider` from `@/lib/features/sync/presentation/notifiers/sync_notifier.dart` and gate any API call on `state.isOnline`. See `@/lib/features/home/presentation/home_screen.dart` for the canonical reconnect-listener shape.
- The `SyncEngine` depends on `@/lib/features/recording/data/repositories/local_recording_repository.dart` (Drift table of pending uploads) and `@/lib/core/network/authenticated_client.dart`. Recordings are created locally first; the engine reconciles them with the server on its own schedule.
- The engine drains the queue **in the order `getPendingUploads` returns it** (FIFO). That order is `createdAt ASC, id ASC` and is owned by `LocalRecordingRepository` (ENG-122): `createdAt` is true enqueue time, `id` is the same-second tiebreaker. The engine itself adds no `ORDER BY`; if the repository's ordering changed, the queue's drain order would change with it. See `@/lib/features/recording/data/repositories/docs.md` for why `recordedAt` is unsafe here.
- The upload pipeline runs in-process through Riverpod: `syncEngineProvider` builds `SyncEngineImpl` with the shared `authenticatedClientProvider` (`@/lib/core/network/authenticated_client.dart`), which reads the access token from `flutter_secure_storage` via `@/lib/core/providers/secure_storage_provider.dart` (the store `@/lib/core/auth/auth_notifier.dart` writes to). Keeping the Android process alive via the foreground service is what lets that in-process credential read keep working while the app is backgrounded; there is no out-of-process worker.
- Connectivity flips originate in `connectivity_plus` and flow through `ConnectivityServiceImpl` → `SyncNotifier._onConnectivityChanged`, which triggers `processQueue()` on offline → online. Screens that need to refresh their own data on reconnect register their own `ref.listen` (the sync layer doesn't notify them directly).
- The global HTTP client at `@/lib/core/providers/http_client_provider.dart` enforces a 15 s connect timeout on native platforms. This is the safety net for the "Wi-Fi connected, no real internet" case that `connectivity_plus` can't detect.

### Core Implementation

- `SyncNotifier.build()` runs `_initConnectivity()` (subscribe → snapshot → refresh pending count) and the notifier never disposes itself implicitly — it's a root-level `NotifierProvider` held for app lifetime. **`_initConnectivity` subscribes to `onConnectivityChanged` BEFORE awaiting the initial `isOnline` snapshot (ENG-139 F19).** `connectivity_plus`'s stream is a broadcast with no replay, so a flip that lands during the `await` would otherwise be lost. A `_sawConnectivityEvent` flag records whether a live event arrived during that window; if it did, the now-stale snapshot is dropped rather than allowed to clobber the fresher value the event already wrote. `_onConnectivityChanged` sets the flag on every event.
- `SyncState` is intentionally synchronous: `isOnline` is a plain bool so callers can do `ref.read(syncNotifierProvider).isOnline` in `initState` / `fetch*` methods without awaiting. The async `connectivityServiceProvider.isOnline` exists for the one early-boot caller in `@/lib/core/auth/auth_notifier.dart` — `refreshSessionIfOnline` (the network half of `tryAutoLogin`, ENG-139 F8) — which runs before Riverpod state has been seeded.
- `SyncEngine.processQueue` filters the pending Drift rows on three conditions — `retryCount < kMaxUploadRetries` (the shared constant in `@/lib/core/config/upload_retry_policy.dart`, which `LocalRecordingRepository.markAsFailed` reads from too), the row is **not** already in `uploading`, and the row is outside its backoff window — then uploads either serially or with `maxConcurrency: 3` on Wi-Fi. Each upload runs the create → upload-url → PUT → confirm pipeline via `ResumableUploadService`. **Connectivity is sampled once per pass, not once per item (ENG-125):** the pass-level gate probes `isOnline` (and `isOnWifi` when `wifiOnly`) before the drain begins; the per-item loops re-probe **only when an upload actually fails**, so a mid-pass network drop still aborts the queue promptly (the serial loop `break`s; the concurrent loop sets a `stopAdmitting` flag so in-flight uploads drain but no new ones start) without polling on the happy path. `_uploadRecording` returns an internal `_UploadOutcome` (uploaded / skipped / failed) so the loops can branch on failure. The storyteller drain (`_processPendingStorytellers`) still probes per storyteller — out of scope for that change. The backoff window is computed by the top-level pure function `backoffWithJitter(attempt, random)`: it returns the ladder rung for the attempt (`5s, 15s, 30s, 60s`, saturating at the last rung) plus additive random jitter in `[0, base*0.5]`, so the effective delay lands in `[base, 1.5*base]`. The jitter de-synchronizes devices that failed at the same instant (e.g. when a server outage clears) so their retries don't realign on one schedule (thundering herd); it never shortens a delay below the base rung. All three drains — recordings, storytellers, and (ENG-403) the metadata outbox — share one private helper (`_isWithinBackoffWindow`) over a single `Random` field, a sharing that started as replacing two duplicated window checks.
- At app startup, before the queue or any upload listener goes live, `LocalRecordingRepository.resetStuckUploading` reclaims rows orphaned in `uploading` by a mid-upload crash (see `@/lib/features/recording/data/repositories/docs.md`). The skip of `uploading` rows in the drain and this startup reclaim are complementary: the reclaim flips orphans back to `local` so they become eligible again, while the skip keeps the drain from racing a row that is genuinely in flight (or was just reclaimed). See Things to Know.
- **The metadata outbox (ENG-403) is one of the engine's three queues, for edits made to a recording the server already has while the server was unreachable.** It is drained first in the pass, ahead of both the Wi-Fi gate and the storyteller queue (see the Wi-Fi-gate bullet below). ENG-399 made those edits land on the local row but nothing ever resent them; this is what resends them. Schema v13 (`@/lib/core/database/docs.md`) adds four columns to `local_recordings` — `metadataSyncStatus`, `pendingMetadataJson`, `metadataRetryCount`, `metadataLastRetryAt` — but the row never stores the edited *value*, only *which* [`PendingMetadataField`](@/lib/features/recording/domain/entities/pending_metadata_field.dart)s are owed (`title`, `description`, `genre`, `subcategory`, `register`, `secondary` — the three secondary-classification columns as one token, since the wire contract only ever clears them together via `clearSecondary` — `cleaningStatus`, and, since ENG-402, `audio`). The row already holds the desired state (every mutation writes it there first), so `SyncEngineImpl._pushPendingMetadata` rebuilds the `UpdateRecordingRequest` by reading the row at send time (`buildPendingMetadataRequest` in `@/lib/features/sync/data/pending_metadata_request.dart`): two offline edits to the same field collapse into one write with no ordering to preserve, and a field this device never touched is never sent — load-bearing because `PATCH /recordings/{id}` is last-write-wins with no ETag, so the size of the body is the size of the window in which this device can clobber another device's edit. **`audio` is the one field not written by `RecordingDetailNotifier`'s metadata mutations.** It is marked pending by `LocalRecordingRepository.replaceAudioAndQueueResend` (`@/lib/features/recording/data/repositories/docs.md`), the write behind the trim editor's gain-only ("boost") save (`@/lib/features/recording/data/docs.md`), and it names the `duration_seconds`/`file_size_bytes` pair rather than a classification/text column — `buildPendingMetadataRequest` sends both whenever it is owed, so the server has the re-encoded file's true duration and size, which it checks the uploaded blob against, before the new bytes arrive (the outbox drains ahead of uploads in the same pass, per the ordering bullet above). This is what keeps a gain-only edit from double-counting the recording on the server the way it did before ENG-402: the edit no longer deletes and re-creates the row at all, so there is no second recording for the outbox or the upload queue to reconcile — see `@/docs/recording-split-semantics.md#what-counts-as-a-split`. The drain goes through `RecordingApiRepository` (injected as `recordingApi`, wired in `@/lib/features/sync/data/providers.dart`) rather than the shared `AuthenticatedClient` directly, so it inherits the one place that already knows what a `PATCH /recordings/{id}` response means — 403 as `ForbiddenException`, 409 as `ConflictException`, and the review flags the server recomputes on every accepted write. `RecordingDetailNotifier`'s five metadata mutations mark fields pending on a `savedLocallyOnly` outcome and clear them on an accepted online write, through `LocalRecordingRepository.markMetadataPending`/`clearPendingMetadataFields` (`@/lib/features/recording/data/repositories/docs.md`); `setStoryteller` is deliberately not one of the five — see Things to Know.
- The recording upload path classifies failures by the typed error model (ENG-103, see `@/lib/core/errors/docs.md`), not by exception subtype. A non-2xx on the create/confirm calls is converted to an `AppException` via `throwForResponse` (`@/lib/core/network/error_boundary.dart`); the catch then routes on `AppException.retryable`. The one exception is intercepted inline at the create call, before the decode: a **409** is parked as `failed_conflict`. The other permanent-fail status, `failed_description`, is decided before the request is issued rather than from a status code (see Status vocabulary below) — retryable leaves go back to the queue via `markAsFailed` — which spends one retry and, when that was the last one, writes `failed_exhausted` itself — non-retryable leaves are stamped permanently-failed via `_markPermanentlyFailed` (whose default status is `failed_exhausted`, not the generic `failed` — see Status vocabulary below). The created recording id and the confirm `gcs_url` are read through the safe-readers (`@/lib/core/serialization/docs.md`), so a malformed field is a terminal `ParseException` rather than an uncaught `TypeError`. The storyteller sync path is deliberately untouched — it has no permanent-fail state.
- `_onConnectivityChanged` calls `processQueue()` automatically on offline → online. This handles upload resumption; it does **not** refresh feature read-paths (those are the screen's responsibility via `ref.listen`).
- Uploads use a per-call `.timeout(_apiTimeout)` (30 s) on create/confirm requests, plus a size-scaled timeout on the PUT to GCS. The 15 s connect timeout on the global HTTP client is independent of these and fires earlier when the TCP handshake never completes.
- **Both sync settings are persisted, not just held in `SyncState` (ENG-355).** `updateSettings` writes `autoUploadWifiOnly` / `autoRemoveAfterUpload` to `shared_preferences` under `sync_auto_upload_wifi_only` / `sync_auto_remove_after_upload`, and `build()` fires `_loadSettings()` to read them back on every fresh notifier (app launch, or a test's fresh `ProviderContainer`). Before this, the Wi-Fi-only flag was state-only and `SyncState`'s default is `true`, so a device that had turned it off went back to Wi-Fi-only on every relaunch and its queue silently stopped draining on cellular. A key absent from storage (first launch) reads back `null`, and `copyWith`'s `?? this.field` falls through to the constructor default (`true`/`true`), so first-launch behavior is unchanged. **`_loadSettings` yields to a choice the user already made:** the `SharedPreferences` singleton is warm by the time the sync notifier builds (startup already called `getInstance()` via `locale_provider` / `project_notifier`), so the load's continuation lands *after* an `updateSettings` triggered a moment earlier and would otherwise overwrite it in state while the correct value sat on disk — the switch would show the wrong position, and the queue obey the wrong value, until the next launch. `updateSettings` sets `_settingsTouched` and `_loadSettings` returns early when it is set. One flag covers both fields because `SyncSettings` always carries both.
- **The Wi-Fi-only gate is decided twice, on purpose, at two different layers (ENG-355).** `SyncNotifier._runQueue` checks `state.autoUploadWifiOnly && !isWifi` **before starting the run** — before the foreground service, before `uploadingId`, before touching `lastSyncAt`/`syncProgress`. (Not literally first: `_refreshPendingCount()` runs ahead of the gate and writes `pendingCount`/`totalQueueSizeBytes`, which is why the chip keeps showing the right number on a blocked pass.) and if it's blocked, sets `SyncState.blockReason` and returns without reporting a run that never happened. `SyncEngine.processQueue`'s own `wifiOnly` parameter (`@/lib/features/sync/data/repositories/sync_engine.dart`) still repeats the same check as a silent early return. The notifier's copy exists because it is the layer that owns user-visible reporting (`lastSyncAt`, `blockReason`) and it must decide before any side effect, not just before the drain; the engine's copy stays as enforcement for any other caller of `processQueue` that does not go through the notifier's gate (i.e. it is not safe to delete just because the notifier now checks first). Both read `_connectivity.isOnWifi` independently — there is no shared cache. **The metadata outbox is exempt from both layers (ENG-403).** `SyncEngineImpl.processQueue` runs `_processPendingMetadata()` before either Wi-Fi check, and `SyncNotifier._runQueue` calls the engine's public `processPendingMetadata()` explicitly on the branch where the Wi-Fi-only gate returns before the engine is ever reached — so a metadata edit goes up on any connection while the upload queue keeps waiting. The rule this reflects: the Wi-Fi-only preference exists to keep megabytes of audio off a metered connection, and a metadata PATCH is a few hundred bytes, not the thing it protects. `processPendingMetadata()` shares `SyncEngineImpl`'s `_isProcessing` bail-if-busy guard with `processQueue`, so the two can never race the same row — whichever gets there first drains it. `blockReason` still reports `wifiOnly` on the notifier's early-return branch — correctly, since it describes the uploads, which really did wait — and nothing else is written there: `lastSyncAt`/`syncProgress` would report a queue run that did not happen, and `pendingCount` counts uploads, which the metadata drain never touches.
- **`SyncState.blockReason` explains a held-back queue; it is not an error field.** It is set only inside `_runQueue` when the Wi-Fi-only gate trips, and cleared (`clearBlockReason: true`) at the top of every subsequent `_runQueue` that clears the gate, inside `processQueue` when the device is offline (so an offline run doesn't leave a stale "Wi-Fi only" verdict behind — offline already has its own visible signal, see Things to Know), and in `syncOne` when it takes the shared upload guard. That last one closes the only hole in "recomputed on every attempt": `processQueue` returns on `if (_isProcessing)` *without* recomputing, so retrying one recording from the detail screen and then tapping the chip used to report the previous pass's verdict while an upload was in flight. Every holder of the guard now establishes the verdict itself. `SyncBlockReason` (`sync_state.dart`) has one member today, `wifiOnly`; there is no "why did an actual upload fail" field — that is still reported per-recording via the existing failed/`failed_*` statuses.
- **`syncNowWithFeedback` (`@/lib/shared/utils/sync_now.dart`) is the one place both sync-triggering UI controls call through.** The header pending chip (`@/lib/shared/widgets/sync_status_indicator.dart`) and Profile → Sync now (`@/lib/features/profile/presentation/profile_screen.dart`) both call it instead of `syncNotifierProvider.notifier.syncAll()` directly: it awaits the sync, then — only if `blockReason == SyncBlockReason.wifiOnly` — shows a localized snackbar (`sync_waitingForWifi`). Before this, a blocked sync was a dead button: the chip animated and returned to the same pending count with nothing explaining why.

### Status vocabulary: client vs server

Several Drift columns hold a free-text status string (no DB-level enum). The values diverge between what the client writes locally and what the server returns over the wire — same column name, different vocabularies and casing. `@/docs/recording-split-semantics.md` is the authoritative field-by-field split mapping; this section just names the state machines.

| Column (client / server) | Where | Values |
|---|---|---|
| `uploadStatus` / `upload_status` | recordings | **client:** `local`, `uploading`, `uploaded`, `verified`, `failed`, `failed_conflict`, `failed_description`, `failed_exhausted`, `failed_missing_file`, `web_uploading` (web). **server:** lowercase — `local`, `uploading`, `uploaded`, `verified`, `upload_failed` (`UploadStatus(StrEnum)` in the API's `app/core/enums.py`, serialized by value). The client's `failed`, every `failed_*` variant and `web_uploading` are client-only; the server's single failure state is `upload_failed`, which the client never writes. `failed` means *a retry is still coming*; the `failed_*` variants are terminal. |
| `cleaningStatus` / `cleaning_status` | recordings | **client:** `none`, `needs_cleaning`; reads `cleaned` from the server. **server:** uppercase enum, e.g. `CleaningStatus.NONE`. |
| `syncStatus` | storytellers (client-only queue) | `synced`, `uploading`, `failed`. The server tracks storytellers by id/timestamps, not this column. |
| `metadataSyncStatus` | recordings (client-only queue, ENG-403) | `synced`, `pending`, `failed_forbidden`, `failed_conflict`, `failed_exhausted`. No server column — these values classify a PATCH outcome (200 / 403 / 409 / other), not something the server reports. See the metadata-outbox bullet below. |
| `status` | recording_sessions (client-only recovery) | `active`, `completed`. |
| `splitting_status` | **server-only** | e.g. `NONE`, `ARCHIVED_AFTER_SPLIT`. The client schema has no equivalent column. |

- **A client `uploaded`/`verified` means "left the device and the server accepted the request" — NOT "durably stored and visible to other clients."** Server-confirmed durability is tracked by the server's own status; the client only ever reads what the server DTO mapper pulls from `upload_status` / `cleaning_status` (`serverRecordingToLocal` in `@/lib/features/recording/data/server_to_local_recording.dart`). Don't treat a local terminal status as proof of server-side completion.
- **Casing crosses the boundary.** The client writes lowercase (`verified`); the server emits uppercase (`VERIFIED`). Any comparison that spans the two must normalize, or go through the safe-readers that map the server DTO into the client's lowercase set (`@/lib/core/serialization/docs.md`).
- The drain-eligibility filter in `processQueue` keys off the client `uploadStatus`: `uploading` is skipped; `local` / `failed` are eligible subject to backoff.
- **`failed_conflict` is a terminal status with a user-driven exit (ENG-71).** The backend deduplicates `POST /api/oc/recordings` by `(project_id, title)`. `_uploadRecording` checks the create response for a 409 **inline, at that one call site**, and parks the row via the same permanent-failure path as `failed` but under `failed_conflict`, so the UI can tell a name clash from a generic upload failure. Deliberately not a `on ConflictException` catch arm around the whole upload body: only the create call deduplicates on `(project_id, title)`, so only a 409 raised *there* is a name clash, and only there does a rename clear it. A 409 raised anywhere else in the upload has no such exit — that row already has a `serverId`, so a rename skips the create branch entirely — and parking it as `failed_conflict` would advertise a way out that leads nowhere. (An earlier revision of this note offered `confirm-upload` as the example of such a 409. That was wrong: `confirm_upload` in `app/services/oral_collector/recording_service.py` loads the recording, emits the Inngest event and returns, with no conflict path at all. The reasoning above stands on its own; the example did not.) Every 409 raised outside the create call therefore falls through to the generic non-retryable handling (`throwForResponse` → `ConflictException` → `_markPermanentlyFailed`, status `failed_exhausted`). `getPendingUploads` does not match `failed_conflict`, so retrying alone can never clear it — only a rename can. Renaming through `RecordingDetailNotifier.saveDetails` calls `resetAndRetry`, which puts the row back to `local` with a fresh retry budget — but only if the server accepts the new title: `PATCH /api/oc/recordings/{id}` also 409s on a clash, `RecordingApiRepositoryImpl.updateRecording` raises `ConflictException` for it, and `saveDetails` returns `titleConflict` without writing anything, so a second clash leaves the row conflicted and re-offers the rename instead of desynchronizing the device from the server. **Visibility is split, on purpose:** the recordings list's *pending* filter (`RecordingsListState.pendingRecordings`) does match `failed_conflict`, so a conflicted recording stays visible and actionable where the user can rename it; the queue-based surfaces do not, because they read `getPendingUploads` — the header badge (`SyncState.pendingCount`, written by `SyncNotifier._refreshPendingCount`) and the upload-queue sheet's own list both exclude it, which is correct: it is not queued work and no amount of draining will move it. **The home screen's total is the one counter that does include it (ENG-355):** it is built from `LocalRecordingRepository.getLocalOnlyStats` — `uploadStatus NOT IN ('uploaded', 'verified')` — not from `getPendingUploads`, and a `failed_conflict` row satisfies that condition (the device has it, the server does not). See `@/lib/features/home/presentation/notifiers/docs.md` for why that is the intended semantics, not an oversight. `requeueFailedUploads` (the recordings list's bulk retry, ENG-404 — a requeue, not the hard delete it replaced) matches `failed` and `failed_exhausted` only, see `@/lib/features/recording/data/repositories/docs.md`, so it leaves a conflicted recording alone; only a rename clears it.
- **`failed_description` is the same shape, for the create rule's other refusal (ENG-354).** `POST /api/oc/recordings` requires a description of at least `minDescriptionGraphemes` (`@/lib/shared/utils/recording_description.dart`); recordings saved before that rule, and split children that inherited a short parent description, would send a null-or-short value and be refused permanently. `_uploadRecording` therefore **pre-flights** the client's own `isDescriptionSufficient` at the top of the create branch and parks the row in `failed_description` **without issuing the request** — the client owns the same rule, so it can decide up front and spend no round-trip. Scoped to the create branch on purpose: a row that already has a `serverId` sends no create, so blocking it would stop an upload the server would accept. Deliberately **not** inferred from the 422: other things 422 on that endpoint (a foreign key the caller got wrong), so reading "422" as "description" would show the wrong explanation. The pre-flight is the only place the status is decided; a 422 always falls through to the generic non-retryable handling. Same visibility split as `failed_conflict`, home total included: excluded from `getPendingUploads` (so retrying alone can never clear it, and the queue surfaces do not count it), matched by the list's *pending* filter (so it stays visible and actionable), counted by the home total (`getLocalOnlyStats`, same reasoning as `failed_conflict` above), untouched by `requeueFailedUploads` (ENG-404 — a bare retry would just hit the same pre-flight). Exit is user-driven: the detail screen shows a banner (`recording_descriptionGapMessage`) routing into the edit-details sheet, which validates with the same predicate, and `RecordingDetailNotifier.saveDetails` calls `resetAndRetry` after a description write on such a row, putting it back to `local` with a fresh retry budget. Unlike a rename there is no server-side second refusal to guard against — the description is only sent at create time — so the write is unconditional. The card and `RecordingStatusSection` give it its own label (`recording_statusDescriptionTooShort`) so it never reads as a generic "Failed". The plain `onRetryUpload` affordance excludes it, like `failed_conflict`: a bare retry would hit the same pre-flight.
- **`failed_exhausted` and `failed_missing_file` close the two ways a row used to be queued and unreachable at once (ENG-377).** `getPendingUploads` matched `local` / `failed` / `uploading` without reading `retryCount`; `processQueue`'s eligibility filter dropped anything at `retryCount >= kMaxUploadRetries`. A row at (`failed`, budget spent) satisfied the first and was refused by the second, forever: the badge counted it, the chip stayed lit, and tapping sync drained zero items and returned without an error to show — `SyncState` has no error field, so nothing could explain it. This was not an edge case: `_markPermanentlyFailed` wrote `failed` **and** `retryCount: maxRetries` in one write, so every non-retryable failure produced it, and the retryable path produced it too on the attempt that spent the last retry. `_markPermanentlyFailed` now defaults to **`failed_exhausted`**, and the budget path is decided inside `LocalRecordingRepository.markAsFailed` rather than by the engine. That placement is the fix, not a detail: the engine could only make that call from a row it had already read, so a failure raised before the read — the platform-channel call inside `_resolveFilePath`, the relocated-path `updateRecording`, the `getRecordingById` itself — counted from zero and left the row at `failed` with a spent budget anyway. `markAsFailed` is the method that re-reads the count, so deciding there makes the invariant hold whatever threw and wherever. The opposite dead end was the file-not-found branch: `_resolveFilePath` returning null called `markAsFailed(incrementRetry: false)`, so the count never advanced, the row never reached the ceiling, and every pass reselected it and skipped it again. That branch now writes **`failed_missing_file`**, terminal because `_resolveFilePath` has already tried all three locations the app uses and deletion is a hard delete — the file is not coming back. Same visibility split as the two statuses above, home total included: out of `getPendingUploads` (so the header badge, the queue sheet and the drain all stop seeing them), matched by the list's *pending* filter, counted by the home total, and — as of ENG-404 — the two statuses split on `requeueFailedUploads` (the recordings list's bulk retry, see `@/lib/features/recording/data/repositories/docs.md`): `failed_exhausted` is exactly what it targets, since a requeue is all that status needs; `failed_missing_file` stays out of its scope, since there is no file left to resend and a requeue would only reproduce the same failure. Neither row is ever deleted for lacking one — each still carries the title, description and classification the user typed and the server never received, and that is worth keeping regardless of whether the audio survives. Exits differ: `failed_exhausted` gets a retry banner routed through `resetAndRetry`, and is the one terminal status `onRetryUpload` does include, because a retry is exactly what it needs; `failed_missing_file` is offered a delete instead, since retrying cannot conjure the audio back. **Rows already stuck on a device are healed by a startup sweep, not just the writer fix.** `LocalRecordingRepository.normalizeExhaustedUploads()` runs once per launch from `@/lib/main.dart` — right after `resetStuckUploading`, before the sync queue or any upload listener goes live — and retires every row still sitting at (`failed`, `retryCount >= kMaxUploadRetries`) to `failed_exhausted` in one `UPDATE`. It is idempotent by construction: the `failed` clause stops matching a row the instant it is retired, so every launch after the first is a no-op for that row. This is the piece that makes the fix visible to whoever reported the bug — fixing the three writers alone would only stop new rows from getting stuck in this shape; it would do nothing for the rows already on their device. The sweep runs from a background `Future.microtask` after the splash gate (`appStartupProvider`) resolves, not before the app's first frame, so there is a real window on every cold start where the list/detail screens can still render a `failed` row with a spent budget before the sweep flips it. `RecordingStatusSection` keeps a literal `retryCount >= 5` branch at `failed` for exactly that window — a literal and not `kMaxUploadRetries`, because it describes what older builds wrote, not the ceiling in force; it renders the same `detail_maxRetries` line `failed_exhausted` uses, so the two paths agree regardless of which one a given frame catches the row in.
- **`metadataSyncStatus` reuses the upload queue's terminal vocabulary where the exit is the same, and invents one where it isn't (ENG-403).** `SyncEngineImpl._pushPendingMetadata` classifies each `PATCH /recordings/{id}` outcome the same way `_uploadRecording` classifies a create: **403** is terminal under a status the upload queue has no equivalent for, `failed_forbidden` — insisting cannot grant permission, and the upload path's blanket `failed_exhausted` exists to offer a retry, which a permission refusal has no use for. **409** is terminal under the upload queue's own `failed_conflict`, because it has the same exit: the backend deduplicates on `(project_id, title)` for the PATCH the same way it does for create, and a rename is what re-marks the row pending with a fresh budget (`markMetadataPending` unions the new fields, resets the retry count, and lifts a terminal status in one write — the exit works because a rename is itself a new pending field). **401 is deliberately not terminal, and spends no retry:** it is the session, not the edit, and every other row in the pass would hit the identical wall, so `_processPendingMetadata` gives up on **the metadata queue** for that pass rather than charging each row's budget for a refusal that was never about that row. It ends that queue only: `processQueue` carries on to the Wi-Fi gate, the storyteller drain and the uploads, which meet the same 401 and do spend their own retries — their existing policy, deliberately untouched. Everything else routes through `AppException.retryable`, the same rule the upload queue uses (see the retryable/terminal bullet above) — a retryable failure spends one attempt via `markMetadataSyncFailed` (which owns the ceiling, mirroring `markAsFailed`), a non-retryable one is parked terminal under `failed_exhausted` via `markMetadataSyncTerminal`. The drain logs through the engine's own `_log`, not `ErrorReporter` — the same choice the upload path already made for its own failures.

### Things to Know

- **Online check is interface-level, not reachability-level.** `connectivity_plus` reports only the OS interface state (Wi-Fi / cellular / none). A captive portal or dead AP still reports online. The 15 s connect timeout in `@/lib/core/providers/http_client_provider.dart` is the current mitigation — it fails fast instead of waiting the OS default (~30 s). A real reachability probe (e.g. `internet_connection_checker_plus`) is a deliberate follow-up, not implemented here. `ConnectivityServiceImpl.isOnline` is uncached, so each call is a real OS query; `processQueue` samples it **once per pass** at the gate and re-probes only after a failed upload (ENG-125) rather than before every item, so the happy path is one probe per pass.
- **The 15 s connect timeout applies only to TCP handshake, not in-flight bytes.** Long uploads/downloads are unaffected once the connection is established. Web uses the bare `http.Client()` because `dart:io HttpClient` is not available there.
- **`syncOne` and `processQueue` are mutually exclusive — bail-if-busy, not serialize.** A single `_isProcessing` flag guards both of the "leaf" upload operations in `@/lib/features/sync/presentation/notifiers/sync_notifier.dart`: whichever starts first wins, and a second upload op that finds the flag set returns immediately rather than queueing behind the first. This keeps two runs from interleaving shared upload state (`uploadingId`, per-file progress, speed samples) or stopping the Android foreground service in one run's `finally` while the other is still uploading. Methods that *delegate* to a leaf — `resetAndRetry` (→ `syncOne`), and `syncAll` / `retryFailed` / the reconnect handler (→ `processQueue`) — must NOT take the guard themselves; a re-entrant acquire would make the inner leaf bail and silently skip the upload, so only the leaf operations acquire it. Accepted gap: tapping reset-and-retry while the queue is running resets the retry count but skips the immediate upload, so that item is picked up by the next `processQueue` run.
- **`getPendingUploads` surfaces `uploading` rows, but the engine drain filters them out.** This split is deliberate: the repository query still returns `uploading` rows because the upload-queue sheet UI (`@/lib/shared/widgets/upload_queue_sheet.dart`) and the header badge (`SyncState.pendingCount`) rely on seeing in-flight work. `getPendingUploads` itself was deliberately NOT narrowed. (The home total gets the same in-flight visibility through a different query, `getLocalOnlyStats` — see the settings-persistence bullet above and `@/lib/features/home/presentation/notifiers/docs.md`.) The eligibility filter inside `processQueue` is the only place `uploading` is excluded, which keeps an in-flight upload from being dispatched a second time and narrows a latent double-dispatch window between `uploadSingle` and `processQueue` — a timing-dependent mitigation, not a hard close: `uploadSingle` does not take the engine's `_isProcessing` guard, so it only helps when the `processQueue` snapshot is read after `uploadSingle` has flipped the row to `uploading`.
- **Stuck-`uploading` recovery is the deterministic crash-recovery path, and it is non-destructive.** A mid-upload app crash leaves a row stuck in `uploading`. `LocalRecordingRepository.resetStuckUploading` runs once at startup (in `@/lib/main.dart`) and flips every such row back to `local`, writing ONLY the `uploadStatus` column — `retryCount`, `lastRetryAt`, `resumableSessionUri`, `serverId`, and `uploadedBytes` are preserved, so the upload RESUMES from its saved offset rather than restarting and the retry budget stays intact. It targets `local` (not `failed`) on purpose: it has to move the row out of `uploading` at all because the eligibility filter above skips that status, and it picks `local` over `failed` because `failed` is the status `requeueFailedUploads`/`hasRetryableFailedUploads` (ENG-404, see `@/lib/features/recording/data/repositories/docs.md` and `@/lib/features/recording/domain/docs.md`) treat as a retryable failure — a crash mid-transfer is not one, and landing on `failed` would expose a recoverable, resumable row to the recordings list's bulk retry, which would reset the very budget and backoff state this method is preserving. It runs unconditionally, after the startup gate resolves (`appStartupProvider` / `restoreSession`, see `@/lib/core/startup/docs.md`) and before the background-sync init / upload listeners, so the queue never observes stale `uploading` state. `uploading` is native-only (web uses `web_uploading`), so on web the call is a harmless no-op.
- **`SyncState.pendingCount` (the header badge) is app-wide, not project-scoped — a known, unfixed gap (ENG-355).** `getPendingUploads()` has no `WHERE projectId` clause: it returns every `local`/`failed`/`uploading` row on the device, across every project the user belongs to. `SyncNotifier._refreshPendingCount` sums the whole list into `pendingCount`, so the badge can read higher than what the currently active project's list/detail screens show (those filter by project). This is separate from — and was not the cause of — the ENG-355 home-total divergence, which came from the home screen's own now-replaced formula (`getLocalOnlyStats` is project-scoped; see `@/lib/features/home/presentation/notifiers/docs.md`). Fixing this is not a one-line scope-by-project change: `_runQueue` calls the same unscoped `getPendingUploads()` to build the list it actually drains, so a fix has to deliberately choose whether the *queue* stays device-wide (drains every project's pending uploads regardless of which one is active) while only the *badge* becomes project-scoped, or whether both narrow together — the two are the same query today and would need to diverge.
- **Existing offline-aware notifier flavors** — keep these in mind when adding new ones:
  - SharedPreferences hydrate-then-fetch: synchronous JSON load in `Notifier.build`, then `_fetchRemoteData` guarded by `isOnline`. See `@/lib/features/project/presentation/notifiers/project_notifier.dart`.
  - Drift cache-first, network-overwrite: load local rows first, then conditionally call API. See `@/lib/features/storyteller/presentation/notifiers/project_storytellers_notifier.dart` and `@/lib/features/recording/presentation/notifiers/recordings_list_notifier.dart`.
  - Secure-storage hydrate + async `connectivityServiceProvider`: only used at app boot by `refreshSessionIfOnline` (the network half of `tryAutoLogin`, see `@/lib/core/auth/docs.md`).
- **A failed upload is retried or terminal by the error's `retryable` flag, and the threshold case is HTTP 429.** The catch in the recording-upload path no longer keeps its own retryable/non-retryable exception taxonomy; it reads `AppException.retryable`. The load-bearing consequence is that a `429` during create/confirm is now retried (it maps to a retryable `ValidationException`) where it previously stranded the row as permanently-failed. `markAsFailed` keeps the row in the backoff queue until the attempt that spends the last retry, which it writes as `failed_exhausted` itself; `_markPermanentlyFailed` is the engine's own terminal write, for refusals that were never about the budget. A non-JSON response body (`FormatException`) and a malformed id/`gcs_url` (`ParseException`) are both terminal — retrying cannot fix a contract violation. `Error` subtypes (e.g. `TypeError`) are intentionally not caught and propagate as bugs.
- **Writes queue offline in exactly two cases: recording uploads, and, as of ENG-403, metadata edits to a recording the server already has.** Storyteller create/update/delete, invite accept, and other mutations still hard-fail offline with a snackbar. The metadata outbox is narrower than "every recording edit": it only tracks the fields `RecordingDetailNotifier` marks pending (title, description, genre/subcategory/register, the secondary triple as one field, cleaning status) plus, since ENG-402, the duration/size pair the trim editor's boost save marks pending directly, on a recording that already has a `serverId`, and `setStoryteller` is excluded outright (see below). A fully generic outbox — covering storyteller mutations too — remains a future feature.
- **`setStoryteller` does not enter the metadata outbox (ENG-403), a known gap, not an oversight.** Its own error handling swallows every exception without distinguishing "server unreachable" from "server refused", so folding it in would first require reworking that handling — the five mutations that do queue already made that distinction through `_pushMetadata`/`_refusal` (`@/lib/features/recording/presentation/notifiers/docs.md`) before ENG-403 needed it.
- **A drained metadata write reproduces the online path's partial-secondary-classification limitation on purpose.** `buildPendingMetadataRequest` omits a null secondary field instead of clearing it, unless all three secondary fields are absent (then it sends `clearSecondary`) — matching `UpdateRecordingRequest`'s existing inability to express "clear only one of three" (`@/lib/features/recording/domain/docs.md`). Fixing it only for the drained path would let an edit sent live and the same edit sent later by the drain disagree about what a partially-filled secondary classification means.
- **Independent awaits in `SyncNotifier` run concurrently, not serialized.** The local-storage reporting and cache-clear helpers (`getLocalStorageUsed`, `clearLocalCache`, `getStorageSnapshot`) fan their per-file / independent reads out with `Future.wait` rather than awaiting in a loop; ordering-dependent steps stay sequential (e.g. `clearLocalCache` still deletes each file before dropping the row that points at it — a row that outlived its file would address nothing). These are fast local operations, so the fan-out is unbounded — the bounded `mapBounded` primitive is reserved for network/server batches (see `@/lib/core/util/docs.md` and ADR-0004). The upload-running fan-out is unrelated and stays under the `_isProcessing` guard above.
- **`clearLocalCache` discards only recordings the server demonstrably already has (ENG-407).** It filters `getAllLocalRecordings()` through `serverHasRecording` (`@/lib/features/recording/domain/server_deletion_policy.dart`, the same predicate the 404 heal paths gate on — ENG-407 deliberately reuses it instead of cloning the condition) — true only when `uploadStatus` is `uploaded`/`verified` **and** `serverId` is non-null and non-empty, because `markAsUploaded` writes both together, so a row saying `uploaded` with no id never finished the round trip and stays local. It deletes the files of that discardable subset, then removes via `LocalRecordingRepository.deleteRecordingsByIds` (`@/lib/features/recording/data/repositories/docs.md`) exactly those rows whose file deletion actually succeeded — a row is the only handle on its file, so dropping one after a failed delete would strand the audio on disk permanently and report space that was never freed; the file that stays keeps its row and the next clear retries it. It returns how many recordings it kept; `_refreshPendingCount()` still runs afterward because the kept recordings are genuine pending uploads and the header badge has to count them. The profile screen (`@/lib/features/profile/presentation/profile_screen.dart`, via `ProfileNotifier.clearCacheAndRefresh` and `showClearCacheResultSnackBar` in `@/lib/features/profile/presentation/widgets/clear_cache_snack_bar.dart`) names that kept count instead of reporting a flat success. This replaced a version that deleted every file and called the repository's own `deleteAllRecordings()` (since removed — it had no other caller) regardless of upload status. A field report is why: an hour-long recording that had waited days in the upload queue was wiped by "Clear local cache" because it existed nowhere else, and the confirmation dialog's "recordings uploaded to the server will not be affected" was true and unhelpful — it spoke for the recordings that were safe and said nothing about the one that was not. Getting the criterion wrong is deliberately asymmetric: keeping a copy the server already has only costs disk space, dropping one it does not costs the recording — which is why both conditions are required rather than either alone.
- **Cold-start race (tracked in ENG-62).** `SyncState.isOnline` defaults to `false` and is only updated after `_initConnectivity()` resolves (a few ms after `build()`). Until ENG-62 lands, the canonical reconnect listener on long-lived screens is what triggers the first real network fetch when a user cold-starts the app while online — don't skip the listener. Symptom if you skip it: cold-start online shows the cache (or empty) and never advances until the user manually triggers a refresh.
- **Checklist for any new screen / notifier that reads from the network:**
  1. Never call the API in `initState` without checking `syncNotifierProvider.isOnline` first.
  2. The notifier `fetch*` method MUST self-guard with `isOnline` as defense-in-depth, even if every caller already does.
  3. First paint renders from cache (Drift / SharedPreferences) or a meaningful empty/loading state — never block on the network.
  4. Long-lived screens add a reconnect listener: `ref.listen(syncNotifierProvider.select((s) => s.isOnline), ...)` and re-call `fetch*` on offline → online. Mirror the shape in `@/lib/features/home/presentation/home_screen.dart`.
  5. Network-required writes hard-fail offline with a snackbar and do not queue, with the one exception above (recording metadata edits, ENG-403).
